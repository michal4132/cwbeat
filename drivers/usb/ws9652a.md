# WS9652A native USB device controller

The controller uses MUSB-compatible endpoint CSRs with a different, word-wide
register map and a separate WS9652A DMA engine. This driver implements full-speed
EP0 control, EP1 IN interrupt, and EP2 IN/OUT bulk transfers for Zephyr CDC ACM.
The original TOP supports additional endpoints, but they are not advertised here.

Packet buffers belong to the UDC instance and are word aligned. The backend
contains no ROM calls, ROM callback tables, or fixed SRAM destinations. No PIO
FIFO port was established from the original firmware; transfers therefore use the
recovered DMA interface. DMA interrupts are masked for USB channels 4–9 only.
The worker obtains completion from the USB controller, not the DMA completion
status: moving bytes into a FIFO does not prove the host acknowledged them.

The `zgmicro,ws9652a-udc` devicetree node supplies the register ranges. A dedicated
preemptible thread serializes polling and requests through the common UDC mutex;
its stack, priority and poll interval use the `UDC_WS9652A_*` Kconfig options.
Zephyr's USB device stack handles descriptors and requests, while its standard
`zephyr,cdc-acm-uart` supplies the shell and console. Isochronous transfers, USB
audio and remote wakeup are not implemented.

The native console uses `0ac8:bb91` and the product string `CWbeat console`.
Recovery remains a separate SBL boot path using `0ac8:38b9`. Opening the shell
must assert DTR. Standard CDC ACM provides no UART transmit-completion query:
shutdown skips an unavailable or DTR-low console and gives a connected console
the existing bounded two-second drain interval. This is best effort, including
any output still in the class queue or deferred logging.

Replacing the ROM backend releases `[0x20000000,0x200051d4)` for application use.
The entire private 64 KiB is one ordinary application RAM region, described by
DTS and placed by Zephyr's standard Cortex-M linker. Recovery uses a one-shot
hardware-register request; no retained SRAM, upper-RAM relocation or crash
record is reserved. Shared peer arena and `memp` allocations remain unchanged;
see the [RAM investigation](../../docs/original-top-ram.md).
Zero-length packets terminating an IN data stage still program and trigger a
zero-length DMA transfer from the valid endpoint buffer, following native TOP
`0x5a61e` → `0x57204`. Control status IN uses the core's RXACK|DATAEND handshake.

| `boot-rom-00000000-00008000.bin` | `600a2863dd7cd940b7b369656431030819c23a515c47d0b39fca6f8f203968fc` |
| TOP, flash offset `0x10000`, length `0x1e400`, CPU address `0x40000` | `0d7b8f82fa37732367a77f46af607297abfd06197f502d5b23e420a96fcd8750` |

The original functions were also executed in Unicorn, with Capstone single-step
inspection of their actual MMIO stores. ROM initialized data was decompressed by
ROM `0xac`; native TOP initialized data was restored using the original scatter
table at `0x5e0dc` and decompressor `0x400ac`. The TOP delay helper was replaced
with a return for this execution; controller and DMA instructions were retained.
This validates recovered instruction sequences, not electrical behavior.

Selected original execution results:

| Original entry | Observed writes |
| --- | --- |
| TOP `0x4a208`, controller initialization | `USB+0x414=0`, then `1`; clear clock-gate bit 5; `USB+0x40c` bits 4/0; `USB+0x400` bit 13; `USB+0x130=2` |
| TOP `0x5a418`, EP1 interrupt IN, MPS 16 | `INDEX=1`, `TXMAXP=16`, `TXCSR=0`, then `0x40` |
| TOP `0x5a418`, EP2 bulk OUT, MPS 64 | `INDEX=2`, `RXMAXP=64`, `RXPACKETS=1`, `RXCSR=0`, then `0x80`; program DMA RX address/count and trigger |
| ROM `0x5130`, EP1 IN packet | DMA TX address/count at `0x4002e138/140`; trigger TX channel 1; `USB+0x170=length`, `INDEX=1`, `TXCSR` bit 0 |
| ROM `0x4da0`, EP2 OUT packet | DMA RX address/count at `0x4002e100/104`; trigger RX channel 2; `RXCSR` bit 15; `RXPACKETS=ceil(length/512)` |
| ROM `0x4d7c`, EP0 receive/acknowledge | Rearm DMA RX first, then `CSR0=0x40`, or `0x48` for DATAEND |

TOP's restored logical-endpoint-to-DMA table at `0x20000584` is
`[0, 1, 2, 3, 4]`. Thus the controller write `USB+0x130=2` does not establish a
permuted EP0 DMA mapping. The backend preserves this native initialization value
without assigning an unverified physical meaning to the word.

Neither the native TOP endpoint configuration nor ROM TX packet primitive sets
MUSB's usual TXCSR DMAENAB bit. The separate SoC DMA control enable and trigger
are the recovered interface. OUT uses the native TOP's manual RXREADY
acknowledgment, rather than ROM's RXCSR AUTOCLEAR setting.

## Register interface

All controller offsets below are relative to `0x40048000`; accesses are 32 bits.

| Offset | Recovered use |
| --- | --- |
| `0x000` | Device address |
| `0x004` | POWER: bit 5 high-speed enable, bit 6 soft connect |
| `0x008`, `0x00c`, `0x018` | TX, RX, bus interrupt snapshots; read once per poll |
| `0x010`, `0x014`, `0x01c` | Corresponding interrupt enables |
| `0x024` | Indexed endpoint selection |
| `0x040`, `0x044` | Indexed TX maximum packet / CSR |
| `0x048`, `0x04c` | Indexed RX maximum packet / CSR |
| `0x050` | Indexed RX byte count at RXREADY |
| `0x06c`, `0x070` | Indexed receive packet count limit / TX byte count |
| `0x0a0` | DEVCTL; native TOP `0x59c62` sets session bit 0 |
| `0x104`, `0x110`, `0x114` | EP0 CSR / RX byte count / TX byte count |
| `0x130` | Native EP0 initialization word, written as 2 |
| `0x388`, `0x390`, `0x394` | Wrapper status acknowledgment, mask, unmask |
| `0x400`, `0x40c`, `0x414` | Controller run bit 13, PHY control bits 0/4, reset sequence |

DMA transfer registers are relative to `0x4002e000`:

| Endpoint | RX buffer | RX capacity | RX actual count | TX buffer | TX length |
| --- | --- | --- | --- | --- | --- |
| 0 | `0x0c8` | `0x0d0` | `0x108` | `0x128` | `0x130` |
| 1 | `0x0d8` | `0x0e0` | `0x10c` | `0x138` | `0x140` |
| 2 | `0x100` | `0x104` | `0x110` | `0x148` | `0x150` |

RX/TX control words are `DMA+0x0c0/0x120`. For endpoint `n`, bit `n+5`
resets the channel, bit `n+10` enables it, and bit `n` triggers it. DMA interrupt
mask words are `0x4002f004/008`, with acknowledgments at `0x4002f00c/010`.
Other DMA channel bits are preserved. The USB clock gate is bit 5 of
`0x4002f900`; it is cleared during initialization.

## Control transfers and cancellation

Native TOP `0x5290e` tests CSR0 SETUPEND at bit 4 and acknowledges it with bit 7.
DATAEND is bit 3, RXREADY acknowledgment bit 6, and TXREADY bit 1. TOP's final
control-IN completion (`0x5a70c` → `0x5a538` with zero length) returns its control
state to SETUP without arming or acknowledging a status-OUT receive. The UDC
therefore advertises automatic status-OUT acknowledgment. Device address changes
are applied after status-IN completion, matching original TOP `0x52918`.

For requests with no data stage and for the final control OUT packet, RXREADY
remains asserted until Zephyr queues its status-IN request. The driver then arms
the next receive buffer and writes CSR0 RXACK|DATAEND (`0x48`), without a separate
TXREADY or zero-length DMA. Completion requires a subsequent endpoint interrupt
with DATAEND and TXREADY clear. This follows the deferred status handshake in
the primary [Linux MUSB EP0 driver](https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/musb/musb_gadget_ep0.c),
whose setup path delays the no-data acknowledgment to avoid SETUPEND errors.
Original TOP also writes `0x48` at `0x52966` / `0x529cc`, but additionally programs
zero-length DMA and writes `0x0a` for status; the deferred handshake is therefore
a MUSB compatibility adaptation, not an exact copy of that original sequence.

Native TOP's RX interrupt path (`0x43982`, EP0 `0x52944`) checks RXREADY and
reads the USB core's packet count: indexed `USB+0x50` for nonzero endpoints and
`USB+0x110` for EP0. It immediately copies from its DMA buffer before clearing
RXREADY; it does not wait for an additional DMA interrupt. The driver follows
that boundary and does not use the DMA completion count to size a USB packet.
TX underrun records an IN token NAKed while the FIFO was empty; it is cleared
without failing the request, following native TOP `0x43900..0x4390e` and Linux
MUSB's `musb_g_tx`. An active non-control IN request also polls its CSR when no
TX interrupt was observed. Completion requires both TXREADY and FIFO_NOT_EMPTY
to clear; a FIFO that is still draining does not complete the request. This
handles the initial CDC zero-length packet used by newer Zephyr, which otherwise
left the console waiting after the endpoint drained. The owner supplies the
active endpoint mask under the UDC mutex after hardware arming. EP0 keeps its
separate handshake. RX overrun/data errors and sent-stall status are reported separately
from successful packet completion.

Non-control OUT acknowledges the copied packet before arming the next DMA
receive. A hardware trace of the previous reverse order showed RXCOUNT growing
from 64 to 65 across the rearm/ACK boundary, leaving the final byte without
another receive event. Regression tests cover that boundary both within one
request and across two queued requests. EP0 retains its separate sequencing;
changing its ACK order did not resolve control-data corruption or status stalls.

For nonzero endpoints, FIFO flushing extends the original TOP's DMA-only
cancellation. EP0 retains DMA-only cancellation because its shared FIFO may
already hold a new SETUP packet when the preceding IN request is cancelled.
The bit positions and double-write sequence follow the primary
[Linux MUSB register definitions](https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/musb/musb_regs.h)
and the `nuke` / `musb_gadget_fifo_flush` paths in the
[Linux MUSB gadget driver](https://raw.githubusercontent.com/torvalds/linux/master/drivers/usb/musb/musb_gadget.c).
They are a compatibility inference supported by the matching observed CSR bits,
not a FIFO-flush sequence found in the stock dumps. TXREADY is cleared while
flushing, and two writes discard both FIFO banks. Ordinary request cancellation
preserves the data toggle; endpoint configuration and clear-halt reset it.

## Control-status stalls and host reset

The former three-second status watchdog and automatic USB disconnect/reconnect
have been removed, including their Kconfig option. A pending status-IN transfer
with CSR0 `0x08` or `0x09` (DATAEND, optionally RXREADY) is not cancelled or
reinitialized solely because time passes.

Normal host bus reset and controller disconnect handling remain. If Zephyr's
event queue is full, a real RESET notification is retried without repeating
cancellation or inventing a reset event. The bulk OUT ACK-before-rearm fix
remains necessary for its separate receive-ordering defect.

The [12 October investigation](../../docs/usb-stall-investigation-2026-10-12.md)
separates the bulk receive fix from missing control OUT data and STATUS_IN
stalls, and records the guarded BT clock patch, native-firmware comparisons
and hardware captures. That BT patch is a separate firmware artifact; building
this TOP application does not install it.

## Validation

The native production image enumerated on macOS with the expected CDC
descriptors and passed a 145-exchange console routine, then passed the same
routine after physical USB disconnect/reconnect. Coverage includes complete
shell responses, 63-/64-/65-/126-character input lines plus CR, sequential and
burst commands, three line-coding baud rates, ten DTR cycles, and ten port
close/reopen cycles. The application shell RX ring is 256 bytes, matching the
CDC RX FIFO; the former 64-byte ring dropped input during these tests. The
descriptor omits a serial number because the SoC has no HWINFO provider.

Before removal of the watchdog on 2026-10-12, clean firmware without the diagnostic module (SHA-256
`a0772eed41a229b46f3c60c1399e9a033c9eca6eda272169441fd8619f3201dc`)
passed 20 cycles of cold reset followed by `power on`. Two EP0 stalls, with
CSR0 `0x08` and `0x09`, recovered automatically through the reconnect mitigation.
A 145-exchange serial stress run passed bursts, packet boundaries, baud changes,
DTR changes and port reopen tests. Graceful `power off`, booting logically off,
then `power on` through audio readiness also passed.

After the guarded BT clock patch and removal of the automatic stall watchdog,
production TOP image `35a81a370ef12aa7b93c2bd6c4cbbccfdffedab4337dc44293627dfe31764445`
passed ten cold-start trials with 1,000 exact replies from 200 writes of 65
bytes, and BT/audio readiness in every trial. The test sent no command retry,
repair newline or USB reset within a trial. Host logs recorded zero USB
transfer-completion errors within the ten trial intervals. The investigation report above
records the firmware, flash verification and workload limits.

The QEMU fixtures cover production MMIO and UDC behavior:
channel isolation, aligned DMA, controller RX counts, data-stage ZLPs, deferred
status acceptance, host-completion gating, nonfatal TX underrun, cancellation,
SETUP preemption, and active TX completion without an observed interrupt.
Lifecycle cases cover stalled DATAEND with and without RXREADY remaining
connected, cancellation by a real host reset, notification queue saturation,
and endpoint callbacks while the controller is disabled.
The [hardware validation report](../../docs/usb-hardware-validation-2026-10-11.md)
records image hashes, host captures, defects found, and reset/recovery results.
The [PMU recovery validation](../../docs/pmu-recovery-validation-2026-10-12.md)
records the subsequent Zephyr-tip CDC issue and its completion-polling fix.

These checks establish enumeration and the tested CDC console traffic. They do
not measure maximum throughput, worst-case latency, sustained audio playback,
or USB suspend/resume behavior.
